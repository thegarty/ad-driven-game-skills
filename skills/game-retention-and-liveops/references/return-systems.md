# Return systems and diagnosis

## Diagnose before adding a system

| Observed pattern | Competing explanations to investigate | Candidate intervention |
|---|---|---|
| Players stop before the first outcome | Confusing input, slow load, crash, weak feedback | Fix the failing journey; reduce explanation before first useful action |
| Players stop at a progression gate | Unclear criteria, undiscovered counter, resource bug, genuine difficulty | Explain the gate; test strategy guidance; then consider balance |
| Players complete content then leave | Content exhaustion, limited mastery, no interesting next choice | A new rule combination, challenge or content extension |
| Session length rises but return falls | Unfinishable runs, friction, idle background time, excessive exposure | Inspect interruption/resume and session boundaries before adding content |
| Ad revenue rises while return falls | Different traffic mix, new ad exposure, measurement changes | Compare equivalent cohorts and cumulative value over a common mature horizon |

The table offers hypotheses, not diagnoses from correlations alone.

## Select a sustainable system

**Daily or rotating challenges:** reuse interesting mechanics with bounded modifiers. Document scoring rules, assisted-run eligibility and what happens at the reset boundary. A new number on an identical task may not supply new interest.

**Collections and build variety:** explain how a new item changes a build or expression. Consider duplicate conversion, inventory clarity and whether one combination dominates. Avoid using collection size as a proxy for meaningful variety.

**Research and offline progress:** make the completed result visible on return. Use the durable completion record to prevent repeated claims. State the elapsed-time policy and how clock anomalies are handled. The player should know what is ready and why it matters.

**Events:** estimate content and QA effort before scheduling. Define eligibility for new and returning players, boundaries in one explicit time basis, delayed claims and end-of-event rewards. Keep a config rollback or disable path appropriate to the implementation.

**Social/competitive systems:** assess matchmaking, score integrity, assisted play, support and moderation needs before adding a leaderboard or chat as a retention tactic. Do not assume every solo game benefits from competitive pressure.

## Overgrowth lesson: visible persistent progress

**Evidence: source-tested; review date 2026-10-25.** A local review found that a run could contribute valid persistent progress without showing that contribution or all unlock conditions in the recap. The UI was changed to display recorded contributions and useful next actions. Completed research also needed a discoverable return notice. These were verified presentation/behaviour fixes, not proof of an increase in human retention.

Apply the lesson by inspecting the difference between actual saved progress and the player's visible understanding. Instrument or observe whether players can state their next goal. Do not add new currencies or grants merely to make the recap more celebratory.
