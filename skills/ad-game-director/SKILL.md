# Ad Game Director

Turn a broad request into useful game work. Preserve the user's genre, engine,
business model and requested stage. Optimise for a game people choose to return
to and its cumulative contribution per acquired player.

## Establish context without an interview loop

Inspect the project brief, game configuration, implementation, prior decisions
and available reports first. Record known context using the
[project-context template](assets/project-context.md); ask only for missing
choices that materially affect the work. Identify:

- Audience, accessibility needs, intended ages and markets.
- Platform, engine/version, existing ad/analytics/purchase services and native bridges.
- Core loop, progression stage, monetisation promises and free route.
- Current stage: concept, prototype, soft launch or live operation.
- Evidence quality: source inspection, source testing, simulation or live measurement.
- Available team time, content capacity, budget and observable success criteria.

Do not silently turn a design request into a production release, paid campaign
or provider-account change. Work within the user's existing authorisation.

## Select the next work

For a new game, define the core decisions and smallest playable slice before
building retention systems around an untested loop. For an existing game,
trace an actual player journey and inspect measurement before proposing new
systems. Missing data is a measurement task, not zero demand or revenue.

Choose the smallest relevant set from the [routing guide](references/routing.md).
If those skills are installed, read their `SKILL.md` files through the agent's
normal discovery/file tools. Names in the routing guide are capability hints,
not commands or assumed tool dependencies. If a specialist is unavailable,
continue using the workflow below and current official documentation; report
the narrower implementation coverage. Do not load every skill or reference.

1. State the current bottleneck and evidence supporting it.
2. Define a concrete change or learning task, its assumptions and alternatives.
3. Produce the requested artifact: prototype/design, implementation, diagnostic
   report, experiment or release assessment. Inspect the selected engine and
   SDK interfaces before writing integration code.
4. Verify the relevant behavior: calculations, progression, input, saves,
   callback handling, native build or cohort measurement. Separate mock/desktop
   checks from device/provider verification.
5. Deliver what changed, evidence, remaining uncertainty and the next decision.

Use the [work-package template](assets/work-package.md) for a cross-functional
handoff. Do not create a roadmap when the user asked for an immediately feasible
fix; complete that fix within the available environment and authorisation.

## Make decisions with the right evidence

Read [evidence and decision rules](references/evidence.md) for audits and
commercial recommendations. Keep longer sessions, return retention and
monetisation separate. Compare mature, comparable cohorts and measure total
value over a stated horizon. Revenue from more ads can coexist with worse
player outcomes; investigate both before calling an experiment successful.

Retain a playable free route, explicit rewarded-offer intent, understandable
purchase promises and recovery from ad unavailability. Audience-specific
requirements and current platform policy constrain the design; do not assume
a general-audience recipe works for a child-directed game.

For grounded examples, read the
[sanitised Overgrowth lessons](references/overgrowth-lessons.md). They are
failure-mode examples, not universal balance settings or demonstrated uplift.
