# Game player support and reviews

Turn a player's problem into a specific recovery or fix, with a clear record of what is known. Keep help accessible to every player, including those who decline ads, purchases, analytics or review prompts.

## Triage the reported problem

Record the platform/build, approximate time and timezone, affected action, expected result and what happened next. Ask for the smallest missing detail that changes diagnosis. Never request passwords, full payment information, advertising IDs or public receipt uploads. Use redacted support aliases and secure evidence routes when ownership verification is required.

Follow the [recovery playbook](references/recovery-playbook.md) for missing rewarded value, lost saves and purchases. Match a report to an immutable opportunity/grant or save revision where available. Preserve recoverable data before reinstall/reset instructions. An ad-close callback does not prove an earned reward, and an earnings dashboard does not identify one player's entitlement.

## Recover within an explicit authority

Distinguish reconciliation of an already-earned grant, restoration of verified paid access and discretionary goodwill compensation. Use a durable idempotent recovery key and an auditable authorized recovery path. If ownership or original value is unknown, explain the limit and offer the documented support route; do not silently alter a production wallet or fabricate a successful restore.

Classify recurring reports by build, stage and failure mode. Escalate save loss, payment errors, inaccessible controls and broad crashes based on harm and reach. Review text is a biased sample of reporting players; combine themes with reproduction and behavioral evidence instead of turning sentiment into an unqualified retention claim.

## Ask for reviews appropriately

Use the [native review recipe](references/native-reviews.md). Request feedback after enough real use at a calm moment, with consistent eligibility independent of predicted rating. Never reward reviews, require positive ratings, ask a sentiment-screening question first or send unhappy players to a private route while only happy players see the store review flow.

Keep a visible support route and an optional store review link available independently. A native prompt request may show nothing; callback completion is not proof of a submitted review. Discover the actual engine bridge and current platform API rather than inventing a Godot method.

## Deliver

Use the [support record](assets/support-record.md) and [feedback/review plan](assets/feedback-review-plan.md). Return the diagnosis, recovery evidence or uncertainty, response draft, issue priority and validation steps. Draft replies plainly and state the actual fixed/distributed status. Sending replies, issuing discretionary compensation or changing live systems must follow the user's authorized scope; drafting and read-only investigation can proceed immediately.
